# 17단계 — 모델을 못 쓰면 메모리만 보고 끝낸다 (축약 경로, exit 5)

16단계(관측)를 구현한 직후 실제 실행에서 문제가 드러났다.

```
ThrottlingException: Too many tokens per day, please wait before trying again.
```

이때 동작이 이랬다.

1. `_ask` 가 예외를 잡지 않아 `ChatBedrock` 의 예외가 노드 밖으로 전파
2. `graph.invoke` → `main()` 을 거쳐 **raw traceback 으로 프로세스가 죽음**
3. `finally` 가 샌드박스만 치우고 **`.heal/` 산출물은 하나도 쓰이지 않음**
   (확인: 실행 후에도 `report.json` 이 7시간 전 것 그대로였다)
4. exit code 규약에 "모델을 쓸 수 없었다" 갈래가 없어 "못 고침(1)" 과 구분 불가

**관측을 강조한 단계 바로 뒤인데 정작 실패하면 아무 근거가 남지 않았다.**

## 핵심 착안 — 검색은 살아 있을 수 있다

메모리 검색은 `ChatBedrock`(Sonnet)이 아니라 **Titan 임베딩**을 쓴다. 별도 한도를 가지므로
LLM 이 죽어도 "과거에 이 계열 버그를 어떻게 고쳤는지" 는 찾을 수 있다. 고치지는 못하더라도
사람에게 **단서**를 남기는 것이 크래시보다 훨씬 낫다.

## 축약 경로의 동작

| 단계 | 축약 경로에서 |
|---|---|
| 테스트 실행 | 그대로 (LLM 안 씀) |
| 수정 대상 추론 | **규칙 기반만** — 스택트레이스 정규식. LLM 폴백은 쓰지 않는다 |
| 버그 리포트 | 건너뜀 |
| 메모리 검색 | **수행한다** — 질의어를 LLM 없이 만든다 |
| 메모리 병합·저장 | **건너뜀** — 요약을 못 만드니 쓰레기를 저장하면 검색 품질만 망친다 |
| 수정안 생성·적용 | 건너뜀 |

질의어는 `{언어} {파일명} {실패 출력 마지막 줄들}` 이다. 저장 형식
(`# 패턴명 ## 증상 ### 원인과 해결`)과 어긋나 **정확도가 낮으므로**, 결과를 "참고 사례" 로만
제시하고 축약 질의였음을 화면과 `report.json`(`memory_degraded_query`)에 명시한다.
실측하면 같은 형식 질의는 거리 0.0, 축약 질의는 0.317 로 임계값(0.3) 밖이었다.

**LLM 을 다시 부르지 않는다.** `ChatBedrock` 이 이미 4회 재시도한 뒤 던지는 예외다. 구조화
파싱 실패와 달리 텍스트 폴백도 시도하지 않는다 — 어차피 실패할 호출의 낭비다.

## exit code 5 와 훅

`3`(전제 실패)으로 뭉개지 않는다. 전제 실패는 그래프 진입 **전에** 툴체인·테스트가 없어
막힌 것이고, 이건 테스트를 돌려 **실제 버그를 찾은 뒤** 모델을 못 써서 멈춘 것이다.
재실행하면 고쳐질 수 있다는 점이 완전히 다르다.

`install-hooks.sh` 의 `pre-push` 도 함께 고쳤다. 기존 분기가 `*) exit 1` 이라 **exit 5 를
그냥 추가하면 토큰 한도가 소진된 날 푸시가 막힌다.** 한도 소진은 코드 결함이 아니라 인프라
제약이므로 `3` 과 같이 경고만 하고 통과시킨다.

## 함께 잡은 것 — 검색이 한 번도 동작하지 않았다

축약 경로를 검증하다 발견했다. `TitanEmbeddingFunction` 에 **`embed_query` 가 없었다.**
chromadb 는 질의를 임베딩할 때 `embedding_function.embed_query(input=...)` 를 호출하므로,
저장(`add`)은 되는데 검색(`query`)은 항상 이렇게 실패했다.

```
AttributeError: 'TitanEmbeddingFunction' object has no attribute 'embed_query'
```

그리고 `MemoryStore.search` 의 `except Exception: return []` 가 그것을 **조용히 삼켰다.**
즉 이 프로젝트의 핵심 기여인 메모리 주입이 **검색 단계에서 한 번도 동작하지 않았다.**
`memory_hits` 가 늘 비어 있었으니 `injected` 도 늘 false 였다.

"메모리는 있으면 좋은 것이지 필수가 아니다" 라는 의도는 옳았지만, 그 관용이 헤드라인 기능이
꺼져 있는 것을 감췄다. 그래서 두 가지를 고쳤다.

- `embed_query`·`embed_documents` 를 위임 메서드로 추가
- `search` 가 실패 사유를 `last_error` 에 남기고, 노드가 `⚠️ 메모리 검색 실패 — 주입 없이
  진행합니다: ...` 로 화면에 드러낸다

## 그 외 정리

- **예상 못 한 예외에도 산출물을 남긴다.** `main()` 이 `except` 절에서 리포트를 쓰고 exit
  code 를 돌려준다. 훅처럼 자동 실행되는 경로에서 traceback 만 남기고 죽으면 안 된다.
- **2차 실패가 1차 원인을 덮지 않는다.** 축약 경로가 이미 "모델 불가" 로 판정했으면 뒤따르는
  실패가 그것을 일반 실패(1)로 내리지 않는다.
- **샌드박스 경로를 노출하지 않는다.** 고치지 못한 경우에도 "진단된 대상" 을 사용자가 아는
  경로로 되돌린다(`_user_path`). 임시 폴더는 곧 지워져 그 경로로는 파일을 열 수도 없다.
- **모델 override 연결.** `--model`(별칭 `sonnet`·`haiku`) 과 `BEDROCK_MODEL_ID`. 기본값은
  AGENTS.md 의 Sonnet 4.5 그대로이고, 한도 소진일에 파이프라인 검증을 이어가기 위한 것이다.
  기본이 아닌 모델로 낸 결과를 착각하지 않도록 화면에 `🔀 모델 override` 를 찍고
  `report.json` 에 `model_id` 를 남긴다.

## 보류

- **온라인 평가와 `--merge-threshold` 0.3 검증** — Bedrock 일일 한도가 회복된 뒤에 한다.
  `--model haiku` 로 대체 실행할 수는 있지만, 임계값은 **기본 스택(Sonnet)** 기준으로 정해야
  의미가 있으므로 모델을 바꿔 측정하지 않는다.
- **검색이 이제 실제로 동작하므로 메모리 효과를 처음으로 측정할 수 있다** — 그 측정도 위
  온라인 실행 시점에 함께 한다.
