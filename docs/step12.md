# 12단계 — 수정안 생성 (S12, 핵심 기여)

`src/agent.py:406 code_update_node` 에 이미 구현되어 있다. **이 프로젝트가 원본 노트북
대비 실제로 기여하는 지점**이다 — 원본은 메모리를 검색해 놓고도 수정 프롬프트에 넣지
않아서 벡터DB가 결과에 아무 기여를 하지 않았다(README 1절 #1).

```python
state.attempts += 1

# 병합 대상(= 충분히 가까운 사례)을 우선 주입한다. 없으면 최상위 1건.
close = [h for h in state.memory_hits if h.distance < self.memory.merge_threshold]
to_inject = close[:2] or state.memory_hits[:1]

memory_block = ""
if self.memory.enabled and to_inject:
    for hit in to_inject:
        hit.injected = True
    joined = "\n".join(f"- ({hit.occurrences}회 발생) {hit.document}" for hit in to_inject)
    memory_block = f"\n[과거 유사 사례 — 참고하십시오]\n{joined}\n"
    self.console.detail(f"→ 과거 사례 {len(to_inject)}건을 수정 프롬프트에 주입")
```

## 확인한 것 — 주입 대상 선정 규칙

| 상황 | 주입 |
|---|---|
| 임계값 안에 든 사례가 있음 | 그중 **최대 2건** (`close[:2]`) |
| 없음 | 최상위 후보 **1건** (`state.memory_hits[:1]`) |

임계값을 못 넘긴 사례도 1건은 넣는다 — "같은 패턴으로 병합할 정도는 아니지만 참고는
된다"는 판단이다. 10단계의 병합 판정과 여기의 주입 판정이 **같은 `merge_threshold`를
쓰지만 목적이 다르다**는 점이 중요하다: 전자는 기록을 합칠지, 후자는 프롬프트에 넣을지다.

주입된 사례는 `hit.injected = True` 로 표시되고, 이 값이 `report.json` 의
`memory_hits[].injected` 로 나간다 — 메모리가 실제로 결과에 기여했는지 사후 검증하는
근거다.

## 결정 — 무관한 사례를 주입하는 폴백을 제거한다

위 규칙의 `or state.memory_hits[:1]` 때문에 **임계값을 아무도 넘지 못해도 최상위 후보
1건이 항상 주입된다.** 이것을 없애고 임계값을 통과한 사례만 주입한다.

- **측정 신뢰도가 이 프로젝트의 존재 이유다.** 지금은 관련 사례가 없어도 항상 뭔가
  주입되므로 `report.json` 의 `injected: true` 가 늘 참이 된다. 9단계에서 `--no-memory` 를
  없앤 뒤 남은 유일한 기여 근거가 `injected` 와 `attempts` 인데, 그 근거를 무의미하게
  만드는 코드다.
- **오염 위험이 제거된다.** 거리가 먼 과거 버그는 수정 방향을 잘못 끌 수 있고, "참고는
  된다" 는 검증된 바 없는 추측이다.
- **주입용 임계값을 따로 만들지 않는다.** 검증되지 않은 상수를 하나 더 늘리는 것은 0.3 에서
  이미 겪은 문제다. `report.json` 에 모든 후보의 거리가 기록되므로, 온라인 검증 실행 때
  "0.3 이 주입을 굶기고 있는지" 를 데이터로 확인하고 **임계값 자체를 조정한다** — 폴백으로
  덮지 않는다. 판단 시점은 `--merge-threshold` 검증과 같다.

`state.is_build_failure` 에 따라 지시문(`objective`)이 달라진다. 문법/컴파일 에러 상태에서

않기 때문에, 먼저 파싱이 되게 만들라고 지시한다.

## 확인한 것 — 프롬프트에 박아 둔 가드레일

- 테스트 파일은 수정 대상이 아니라고 명시 (G1 — 단, 프롬프트는 보조 수단이고 실제 차단은
  어댑터·`is_source_file` 수준의 구조로 한다)
- 공개 함수 이름·시그니처 유지 → 테스트를 우회하는 편법 차단
- 전체 파일 내용만 출력, 설명·코드 펜스 금지 → `_strip_fence` 로 한 번 더 정리

## 결정 — 파일 전체 재생성을 구조로 검증한다 (G9)

프롬프트가 "수정된 파일의 **전체 내용**만 출력하십시오"라고 지시하므로 LLM 이 파일을
통째로 다시 쓴다. 그래서 고쳐야 할 함수와 **무관한 코드까지 매번 재생성**되고, LLM 이
관련 없는 함수를 조용히 빠뜨리거나 바꿔도 테스트가 그 부분을 덮지 않으면 그대로 통과한다.
파일이 커질수록 위험이 커지는데, 지금 방어선은 "프롬프트로 부탁하기"와 "사람이 diff 검수"
둘뿐이다 — G1~G8 이 전부 구조로 막는 이 프로젝트의 원칙에서 벗어난 유일한 지점이다.

**수정안 생성 직후, 수정 전/후 소스의 최상위 심볼 목록(함수·클래스 이름과 인자 수)을
비교해 무관한 심볼이 사라지거나 시그니처가 바뀌면 그 수정안을 거부하고 재시도로 돌린다.**

- **전체 파일 생성 방식 자체는 유지한다.** LLM 이 만든 unified diff 는 줄 번호·컨텍스트가
  어긋나 적용 실패가 잦고, 재시도 상한이 3회(G5)인 구조에서는 적용 실패로 시도를 낭비하는
  쪽이 더 위험하다.
- **놓을 자리는 `src/tools.py`** — 언어별 지식은 전부 `LanguageAdapter` 에 모여 있다
  (`style_hint`, `is_source_file`). "이 언어의 최상위 심볼을 뽑는다"도 같은 자리에 둔다.
  Python 은 `ast`, JS/Go 는 정규식 수준으로 시작한다.
- **파싱이 안 되면 검증을 건너뛰고 통과시킨다.** 검증 실패가 수정 자체를 막으면 안 된다
  (9단계 메모리와 같은 원칙 — 보조 장치가 본 기능을 멈추게 하지 않는다).
- **대상 파일 자신의 변경은 허용한다.** 막는 것은 "고치라고 하지 않은 심볼이 사라지거나
  시그니처가 바뀌는 것"뿐이다. 기존 프롬프트 지침("공개 함수의 이름과 시그니처는 그대로
  유지")을 구조로 뒷받침하는 것이므로 새 제약이 아니다.
